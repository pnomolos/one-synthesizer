Signal flow: MIDI in, OSC out

A note never passes through the Linux UI on its way to a voice. The XMOS voice controller takes MIDI in, decides which voices play, and emits OSC to the voice cards.

Sections 1 to 5 describe the instrument as shipped. Section 6 is the modification this project makes to get per-note MPE. Each diagram can be read at three levels: simplified, for anyone who knows MIDI; intermediate, showing the stages; and detailed, showing every step and message.

1. The whole path

The frontend and the voice controller share an internal USB-Ethernet link. The rear Ethernet jack is also routed through the voice controller, so a hung controller takes the whole box off the network.

2. External controller

USB and DIN MIDI terminate on the voice controller. Each message becomes an internal event carrying its type, input port, MIDI channel, note, raw 14-bit data and velocity. The router offers the event to each of the three timbres; a timbre accepts it if it passes that timbre's filter for that input port. Matching is independent per timbre, so two timbres on the same channel layer.

A voice v lives on card v / 2, slot 1 + v mod 2, which is why card addresses are only ever /v1 or /v2.

The frontend sees none of this directly. It learns which notes are sounding from the echo the controller sends back on UDP 7772.

3. Built-in keyboard

The keybed and the left-hand controls are not MIDI and do not arrive over the OSC performance port. They enter the voice controller as local events with no channel (the channel field is −1).

Captures show it busy whenever keys or the pad move and show nothing on 7771, which establishes that local input bypasses the OSC performance port. 5. The frontend's own notes

The sequencer and arpeggiator live in the Linux frontend, so their notes do cross the performance port, as raw MIDI bytes wrapped in OSC:

/r/sq/0/midi-arp ,iii 144 60 100     note-on, channel 1, note 60, velocity 100

The same triple is accepted on several router addresses (/r/midi, /r/midi-force, per-timbre /g/<t>/midi). Details on the protocol page.

6. Per-note MPE

As shipped, bend, pressure and timbre reach every note a Synth is holding, so an MPE controller's per-finger expression collapses into one value. The voice cards, though, already accept those three messages addressed to a single voice; the stock controller never sends them that way. This project changes the voice controller, and nothing else, so that it does.

  1. One timbre is designated the MPE zone and accepts notes from every channel.
  2. Each allocated voice remembers the channel its note came in on.
  3. Bend, pressure and CC74 on a member channel go only to voices tagged with that channel. The card sums them into pitch, amplitude or filter every tick, independent of gate state.
  4. The timbre-wide messages for that timbre are dropped, since per-voice and timbre-wide writes land in the same slot and the last writer wins.

All three axes have been verified on one instrument, on one firmware version. The other two timbres behave as shipped.

Known boundary: the built-in XY pad still acts on the MPE timbre as a global brightness control, because it arrives by the local path in section 3 and never crosses the point where the timbre-wide messages are dropped.
